= iceberg-zero-copy-append
:toc: left
:source-highlighter: rouge

Appends one Iceberg table into another by metadata only: the data files
referenced by the source's current snapshot are committed into the target in
a single atomic fast-append snapshot. *No data is read, rewritten, or moved.*

[cols="1,3"]
|===
| Layer | ops (cross-layer maintenance)
| Schema version | 1
| Flow | `IcebergZeroCopyAppendAction` (single driver-side action, no dataflow)
| Output | new snapshot on `<catalog>.<tenant>_<layer>.<target.table>`
|===

== Semantics

This is **UNION ALL, not MERGE**. Rows are never deduplicated, matched, or
resolved by key — the job can only attach the source's existing files to the
target's metadata. If the target may already contain rows for the same
business keys, this job is the wrong tool; use `cdc-silver-merge` or a
copying insert.

The commit is atomic: every validation runs before the append, and any
failure leaves the target exactly as it was. Re-running after success is a
no-op (see <<idempotency>>).

== Example

[source,hocon]
----
job    { template = "iceberg-zero-copy-append", schema-version = 1 }
tenant { id = "acme", storage-root = "s3a://lake/acme" }
source { table = "orders_2025" }            # layer defaults to silver
target { table = "orders" }
----

[cols="2,1,1,3", options="header"]
|===
| Key | Type | Required | Description

| `job.template`
| string
| no
| Must be `iceberg-zero-copy-append` when present.

| `job.schema-version`
| int
| no (default `1`)
| Declared schema version; must be `1`.

| `job.name`
| string
| no
| Flow name. Default: `<tenant>-<target.table>-zero-copy-append`.

| `tenant.id`, `tenant.storage-root`
| string
| yes
| Tenant identity. Both tables resolve inside this tenant's namespaces;
  cross-tenant appends are not expressible by design (the physical files
  would cross tenant storage boundaries).

| `source.table`, `target.table`
| string
| yes
| Bare table names, resolved to `<catalog>.<tenant>_<layer>.<table>`.

| string

| `target.catalog`
| string
| no (default `hms`)
| Iceberg catalog used for **both** tables.
|===

== Preconditions enforced by the job

Each of these would silently corrupt the target if the append went ahead, so
the job refuses fail-fast (target untouched):

Field-ID schema identity::
Iceberg reads parquet columns by the field ID stamped into each file, not by
name. The schemas must be identical *including field IDs* — two tables with
the same DDL today but different schema-evolution histories (a column
dropped and re-added, different add order) have different IDs, and the
imported files would read as nulls or as the wrong columns. The job compares
full schemas by ID and additionally refuses when the source's ID counter is
ahead of the target's (`lastColumnId`), because IDs left behind by columns
the source dropped would collide with columns the target adds later.

No row-level delete files::
Position/equality delete files (format v2 merge-on-read) cannot be carried
over — their effect depends on sequence numbers assigned at commit time in
the source. Appending only the data files would resurrect deleted rows. If
the source has live deletes, compact it first
(`CALL <catalog>.system.rewrite_data_files(...)`) and re-run; note that the
compaction itself rewrites data.

Compatible partition specs::
Data files carry partition tuples tied to a spec; the source's current spec
must be compatible with the target's (same transforms over the same
columns). Unpartitioned→unpartitioned is fine.

[#idempotency]
== Idempotency

The appended snapshot records the source table and source snapshot ID in its
summary (`lakehouse.zero-copy-append.*`). A re-run with the same source
state is a no-op, so orchestrator retries are safe. The window is bounded by
the target's snapshot retention: once `expire_snapshots` drops the recording
snapshot's summary from history, a re-run would append the files again as
duplicates. Do not re-run after the target's retention horizon has passed
the original run.

== Accepted limitations and operating constraints

These are consequences of "no data movement" that the job *cannot* enforce.
They are accepted deliberately; the orchestration layer owns compliance.

**After the append, both tables reference the same physical files, which
live under the source table's location.** Iceberg assumes each table owns
its files exclusively, so every maintenance operation becomes a loaded gun:

* `DROP TABLE <source> PURGE` deletes the target's data. Drop the source
  **without** `PURGE` (metadata-only drop).
* `expire_snapshots` on the source can delete files the target references
  (as soon as the source itself rewrites or deletes rows and expires the old
  snapshots). Symmetrically, `expire_snapshots` on the target can delete
  imported files the source still references.
* `remove_orphan_files` on the target never sees the imported files (they
  are outside the target's location) — they will never be cleaned up by the
  target, only by dropping them together with the source's storage prefix
  once the target no longer needs them.

**Required lifecycle: the source is retired at append time.** The supported
pattern is consolidation — after a successful run the source is frozen
(no more writes, no maintenance), then dropped without purge. Its storage
prefix may be deleted only when the *target* no longer references the files
(i.e. after the imported rows were rewritten by compaction/updates *and* the
old target snapshots expired). If both tables must stay live and writable,
zero-copy is the wrong tool — use a copying insert.

Other accepted consequences:

* Readers of the target need storage access (credentials, network) to the
  source's location, permanently, until the imported files are rewritten.
* Target-level statistics (Puffin/NDV) go stale until recomputed; per-file
  column metrics travel with the manifests and stay correct.
* Schema evolution on the target after the append is safe *only* going
  forward (the `lastColumnId` guard above protects the import moment, and
  Iceberg never reuses IDs within one table's history afterwards).
* An empty source (no snapshot, or no data files) is a successful no-op.

== Failure modes covered by integration tests

`integration-tests/.../IcebergZeroCopyAppendIntegrationTest.kt` pins each
refusal and the documented hazard:

* identical-looking schemas with diverged field IDs → refused, target unchanged
* source field-ID counter ahead of target (dropped column) → refused
* source with merge-on-read delete files → refused, target unchanged
* partitioned source into unpartitioned target → refused
* re-run after success → no-op (no duplicate rows, no new snapshot)
* happy path asserts the target's new files are the source's files
  byte-for-byte (same paths — nothing copied)
* `DROP TABLE source PURGE` after an append breaks the target — the
  documented ownership hazard, demonstrated
